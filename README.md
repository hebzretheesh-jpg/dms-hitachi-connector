# dms-hitachi-connector

Go implementation of the DMS binary-content connector. It preserves the existing DMS REST contract while storing content in a Hitachi Hitachi-compatible backend.

## Endpoints

- `GET|POST|PUT /dss/api/put/{tenant_id}`
- `GET /dss/api/ping`
- `GET /dss/api/stats/{file_id}`
- `GET /dss/api/get/{file_id}`
- `GET /dss/api/getimage/{file_id}/{page_number}?scale=1.0`
- `GET /metrics`
- `GET /healthz`
- `GET /readyz`

## Storage Layout

Objects are stored under `HITACHI_OBJECT_PREFIX`:

- binary content: `/<HITACHI_OBJECT_PREFIX>/document/{file_id}`
- metadata JSON: `/<HITACHI_OBJECT_PREFIX>/meta/{file_id}.json`
- rendered PDF previews: `/<HITACHI_OBJECT_PREFIX>/thumbnail/{file_id}_page_{page}_dpi_{dpi}.png`
- quarantined binaries when metadata write fails: `/<HITACHI_OBJECT_PREFIX>/failed/{file_id}__{original_filename}`

This keeps the northbound API stable without requiring a separate metadata database.

### Directory Structure

For the default root `HITACHI_OBJECT_PREFIX=/connector/dms`, the effective layout looks like this:

```text
/connector/dms/
├── data/
│   └── {file_id}
├── meta/
│   └── {file_id}.json
├── images/
│   └── {file_id}_page_{page}.png
└── failed/
    └── {file_id}__{original_filename}
```

- `document/` stores the original uploaded binary.
- `meta/` stores the metadata record used by `stats`, `get`, and `getimage`.
- `thumbnail/` stores cached PNG previews for PDF pages.
- `failed/` stores binaries that were uploaded successfully but could not be paired with metadata.

### Metadata Schema

Each metadata file under `meta/{file_id}.json` is stored as JSON with this structure:

```json
{
  "file_id": "2516583547427874372",
  "tenant_id": "test-tenant",
  "storage_path": "/connector/dms/data/2516583547427874372",
  "size": 49672,
  "content_type": "application/pdf",
  "uploaded_at": "2026-04-17T03:00:00Z",
  "tags": {
    "tenant_id": "test-tenant",
    "original_filename": "sample.pdf"
  }
}
```

Field details:

- `file_id`: generated numeric object ID returned by the upload API
- `tenant_id`: tenant from `/dss/api/put/{tenant_id}`
- `storage_path`: S3 object path for the stored binary
- `size`: uploaded object size in bytes
- `content_type`: content type from the incoming request, or detected from file bytes when missing
- `uploaded_at`: UTC timestamp written by the connector
- `tags.tenant_id`: repeated tenant marker for convenience
- `tags.original_filename`: original uploaded file name

## Runtime Behavior

- Uploads stage request content to a local temp file, then stream that file to S3.
- IDs are generated by a Snowflake-style numeric generator and require a unique `WORKER_ID` per running instance.
- `/dss/api/ping` returns success only when S3 is reachable and the ID generator has not detected a backward clock jump.
- `/readyz` checks S3 reachability.
- `getimage` returns original bytes for image content, and PDF previews for PDF content.
- PDF previews are cached back into S3 under `thumbnail/`.
- If binary upload succeeds but metadata upload fails, the binary is moved into `failed/` as a best-effort quarantine path.

## Metrics

The connector exposes Prometheus-style metrics at `GET /metrics`.

### Generic Request Metrics

- `dms_connector_requests_total{endpoint,method,status}`
  Total request count by logical endpoint, HTTP method, and response status.
- `dms_connector_request_duration_seconds_sum{endpoint,method}`
  Sum of observed request durations by endpoint and method.

### Health Metrics

- `ping_success_count`
  Number of successful `/dss/api/ping` checks.
- `ping_failure_count`
  Number of failed `/dss/api/ping` checks.
- `hitachi_connection_fail_count`
  Number of S3 connectivity-related failures observed by the connector.

### Upload Metrics

- `hitachi_upload_success_count{bucket_name}`
  Successful S3 writes performed by the connector.
- `hitachi_upload_fail_count{bucket_name}`
  Failed S3 writes performed by the connector.
- `file_upload_success_count{bucket_name}`
  Successful DMS upload requests that completed file and metadata creation.
- `file_upload_fail_count{bucket_name,object_name}`
  Failed DMS upload requests keyed by object ID.

### Download Metrics

- `hitachi_connection_get_stream_success_count{bucket_name}`
  Successful S3 download stream opens.
- `hitachi_connection_get_stream_count{bucket_name,object_name}`
  Failed S3 download stream opens.
- `file_download_success_count{bucket_name}`
  Successful DMS file download responses.
- `file_download_fail_count{bucket_name,object_name}`
  Failed DMS file download responses.

### Metadata and Preview Metrics

- `get_stats_success_count{bucket_name}`
  Successful `stats` lookups.
- `get_stats_fail_count{bucket_name,object_name}`
  Failed `stats` lookups.
- `get_pdf_image_success_count{bucket_name}`
  Successful PDF-to-image responses.
- `get_pdf_image_fail_count{bucket_name,object_name}`
  Failed PDF-to-image responses.

## Configuration

Required:

- `HITACHI_ENDPOINT=https://<your-s3-endpoint>`
- `HITACHI_ACCESS_KEY_ID=<access-key>`
- `HITACHI_SECRET_ACCESS_KEY=<secret-key>`
- `HITACHI_BUCKET=<bucket-name>`

Optional:

- `LISTEN_ADDR=:9082`
- `READ_TIMEOUT=30s`
- `WRITE_TIMEOUT=5m`
- `IDLE_TIMEOUT=60s`
- `HITACHI_OBJECT_PREFIX=/connector/dms`
- `HITACHI_HTTP_TIMEOUT=60s`
- `TEMP_DIR=/tmp`
- `DOWNLOAD_CACHE_DIR=/tmp/dms-download-cache`
- `DOWNLOAD_CACHE_MAX_FILES=128`
- `MAX_UPLOAD_BYTES=67108864`
- `PDF_RENDER_DPI=144`
- `WORKER_ID=0`

`WORKER_ID` must be unique per connector instance and must be in the range `0..1023`.

## Local Run

This repository now assumes a separate Hitachi-compatible storage endpoint is already available.

1. Build the connector:

```bash
cd /home/cdit/dms-hitachi-connector
go build -o bin/dms-hitachi-connector ./cmd/server
```

2. Set required environment variables and start the server:

```bash
export HITACHI_ENDPOINT=http://127.0.0.1:9000
export HITACHI_ACCESS_KEY_ID=minioadmin
export HITACHI_SECRET_ACCESS_KEY=minioadmin
export HITACHI_BUCKET=dms-connector
export HITACHI_OBJECT_PREFIX=/connector/dms
export WORKER_ID=0
export LISTEN_ADDR=":9081"

./bin/dms-hitachi-connector
```

Or use the helper script:

```bash
./start-local.sh
```


If `k6` is not available, parallel `curl -F "bin=@..."` requests also work for basic upload benchmarking.

## Repairing page counts of migrated documents

Documents migrated from the old DSS were stored with `page_count = 1`, so the
viewer showed only their first page. The connector repairs a document the
first time it is viewed, but a large PDF may still show one page on that first
view. To fix every migrated document up front, run the one-time backfill:

```bash
go build -o bin/repair-page-counts ./cmd/repair-page-counts

# Uses the same HITACHI_* / TEMP_DIR environment as the connector.
# pdfinfo must be installed (pdftoppm too when using -prewarm).
./bin/repair-page-counts -dry-run      # report how many documents need repair
./bin/repair-page-counts -workers 4    # repair them
```

- Safe to stop with Ctrl+C and run again: repaired documents are skipped.
- Failed document IDs are written to `page-count-failures.txt`; retry them
  with `-cid $(paste -sd, page-count-failures.txt)`.
- `-prewarm` also renders every page into the preview cache (much slower);
  without it, pages are rendered the first time they are viewed.
- `-limit N` stops after N documents, useful for a trial run.
